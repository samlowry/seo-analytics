Дата: 2026-08-11. Участники спора: `seo-arch`, `infra-block`, `product-ux`, `risk-comp`,
`devil`. Тиммейты переписывались напрямую и опровергали друг друга; ниже — то, что

## 0. Расщепление ответа по User-Agent — измерено, воспроизводимо

**Утверждение «клоакинга по User-Agent нет» (`CLAUDE.md`, `mostbet-redirect-scheme.md`
§7 и §9, `BRAINSTORM-setup.md` §5) верно только для RS-IP и НЕВЕРНО для US-IP.**
Оно было измерено в одной точке выхода и обобщено на все — ровно то нарушение правила
репозитория, на котором проект уже горел дважды.

Замер лида, US-IP этого окружения, 2026-08-11, один инструмент, один момент,
один алгоритм хеширования:

| клиент | код | тело | sha256 (первые 16) |
|---|---|---|---|
| без UA | `204` | 0 | `e3b0c44298fc1c14` |
| Chrome UA | `204` | 0 | `e3b0c44298fc1c14` |
| **UA с `Googlebot/2.1`** | **`200`** | **9 580 B** | `76d010d64c1e8ad3` |

Триггер — **подстрока `Googlebot/2.1`, регистрозависимая**:

| строка UA | код |
|---|---|
| `Googlebot/2.1` | **`200`** |
| `googlebot/2.1` | `204` |
| `GOOGLEBOT/2.1` | `204` |
| `Googlebot` (без версии), `GoogleOther`, bingbot, YandexBot | `204` |

Регистрозависимость и отсутствие обратного DNS указывают на **сигнатурное правило
(дефолтный bot-allowlist CDN)**, а не на замысел. Но эффект от намерения не зависит.

**Блокировка США обходится 13 символами в заголовке**, с постороннего датацентрового
адреса вне сетей Google.

### Сопутствующие факты, снятые тем же прогоном

| проверка | результат |
|---|---|
| `Sitemap:` в `robots.txt` апекса | **отсутствует** |
| `/sitemap.xml` | `404` |
| `8unx689.com` под Googlebot-UA | `451` — **исключения на зеркале нет**, дефект локализован на апексе |
| `mostbet-pl.com`, Chrome vs Googlebot | `200/166 106` vs `200/166 106`, хеши совпадают — **UA-ветвления нет** |
| `guidebook.mostbet.com`, Chrome vs Googlebot | размер тот же, хеши **разные** — но два запроса **одним и тем же** UA тоже дают разные хеши: отличие в одной строке `Served from: … @ 18:57:00 by W3 Total Cache`. **UA-ветвления нет**, это таймстамп кэша |

Проверка `infra-block` по 10 региональным доменам и моя выборочная сходятся:
**расщепление по UA есть только на апексе.** Это снимает блокирующее предусловие
схемы 1A в плюс — кластер можно строить.

### Ещё четыре дефекта разметки апекса (проверяются согласующим за минуту)

Из 21 заявленного альтерната **недостоверны минимум 4**:

| альтернат | что не так |
|---|---|
| `x-default` → `mostbett.bet` | посторонний домен, 6 URL |
| `cz-CZ` | `cz` не язык по ISO 639-1 (чешский — `cs`); «Google Search ignores that part of the annotation» |
| `by-BY` | `by` не язык (белорусский — `be`); там же |
| `az-AZ` → `mostbetaz.biz` | **`301` → `http://mostbetazerbaycangiris.net/`** — не страница, а редирект, да ещё на `http` |
| `tr-TR` → `mostkupon.tr` | **`301` → `http://mostbettr.asia/`** — то же |

Последние два убийственны для взаимности: подтвердить её обязан **URL, названный в
аннотации**, а он не страница. Эти альтернаты не могут заработать в принципе.

### Цепочка обвала индекса — теперь из замеров, а не из гипотез

1. [ФАКТ — замер, US-IP] клиент с `Googlebot/2.1` получает `200` + шелл.
2. [ФАКТ — замер, US-IP] ему же `/api/v3/common/redirect` отдаёт
   `{"redirect":true,"domain":"8unx689.com"}`.
3. [ФАКТ — замер, US-IP] `robots.txt` отдаётся ему `200`, сканировать разрешено.
4. [ФАКТ — замер, декомпиляция] гейт подменяет **только хост**, сохраняя path и query —
   значит редирект существует **для каждого URL**, а не только для корня.
5. [ФАКТ — документация] JS-`location` классифицирован Google как **постоянный**
   редирект: «the indexing pipeline uses the redirect as a signal that the redirect
   target should be canonical»
   (https://developers.google.com/search/docs/crawling-indexing/301-redirects).
6. [ФАКТ — замер, US-IP] `8unx689.com` отдаёт с этого же IP **`451`**.
7. [ФАКТ — документация] «All `4xx` errors, except `429`, are treated the same: Google
   crawlers inform the next processing system that **the content doesn't exist**»
   (https://developers.google.com/search/docs/crawling-indexing/http-network-errors).

**Итог, сформулированный ровно по замерам и не сильнее:** из США API выдаёт краулеру
указание перейти на домен, который из США отдаёт `451`; механизм, отработав, приводит
краулера в тупик. Формулировку «каждый URL апекса заявляет постоянный перенос на
несуществующую страницу» **сознательно не используем** — она сильнее того, что
измерено: JS-`location` стоит последним по надёжности интерпретации, и Google прямо
предупреждает «Google might never see it if rendering of the content failed».

Это объяснение обвала конкурирует с прежним (soft 404 на пустом шелле) и **не
отменяет его** — обе версии идут в отчёт равноправно, дискриминатор один: категории
отчёта «Страницы» в Search Console.

### Прямое противоречие с предписанием Google

> «if you block USA-based users from accessing your content, but allow visitors from
> Australia to see it, your server **should block Googlebot if it appears to be coming
> from the USA**, but allow access to Googlebot if it appears to come from Australia»
> — [ФАКТ — документация] https://developers.google.com/search/docs/specialty/international/locale-adaptive-pages

Сделано ровно наоборот: пользователь из США получает `204`, бот — `200` и маршрут
в сервис.

**Оговорка, которую нельзя терять:** подменялась строка `User-Agent` с постороннего
датацентрового адреса. Как поведёт себя настоящий Googlebot с IP из AS15169
(Google верифицирует бота обратным DNS) — **[ГИПОТЕЗА]**, закрывается только логами
эджа. Обвинять в клоакинге по спам-политике **нельзя**: её определение содержит
элемент намерения («with the intent to manipulate»), а сигнатурный характер триггера
указывает на дефолт CDN.

### Что из этого следует для приоритетов

- Раздел 1.1 («разметка на апексе физически не доезжает до Googlebot») **опровергнут
  фактически** — доезжает. Но носителем оказалось UA-исключение, то есть ровно то, что
  запрещает наша же красная линия 6.1. Поэтому апексный пакет заявок не вырос в
  приоритете, а **схлопнулся в «удалять, не добавлять»**.
- Появилась заявка вне очереди — **инцидент И-1** (раздел 5): устранить зависимость
  ответа от строки `User-Agent` при неизменной стране. Выравнивать **вниз**: в закрытых
  гео `204` всем клиентам без исключения.
- Заявка №3 прежней редакции (`204` → `200` для закрытых гео) **умерла**: `204` для
  США — предписанное Google поведение, а не дефект.

## 1. Пять находок, которые меняют вводную

**1.1. Ставка «апекс = узел передачи сигналов» может быть нереализуема физически —
до всякого комплаенса.**

> «Google egresses primarily from IP addresses in the United States. In case Google
> detects that a site is blocking requests from the United States, it may attempt to
> crawl from IP addresses located in other countries.»
> — [ФАКТ — документация] https://developers.google.com/search/docs/crawling-indexing/overview-google-crawlers

> **204:** «Google wasn't able to receive any content and therefore can't process it.»
> — [ФАКТ — документация] https://developers.google.com/search/docs/crawling-indexing/http-network-errors

[ФАКТ — замер, US-IP] апекс и его API отдают `204`, тело 0 байт.

Следствие: из основной точки выхода Googlebot `<head>` апекса **не читается никак** —
не «хуже», а вообще. Тезис `CLAUDE.md` «единственная возможная роль апекса — узел
передачи сигналов» надо понизить до **[ГИПОТЕЗА]**: он верен только если бот доходит
до апекса из открытого гео, а этого никто не проверял. `seo-arch` снял свой
центральный тезис о приоритете апекса публично.

Что говорит против сильной версии «Googlebot апекс не видит»: «primarily» ≠ «only»,
и `mostbet.com` в индексе присутствует. Эта гипотеза уже умирала один раз
(`HANDOFF.md` §6) — второй раз её воскрешать в виде факта нельзя. Но `devil`
заметил то, чего не заметили тогда: регрессию выкатили 3–5 недель назад, и запись
в индексе может быть **остаточной**. Закрывается Search Console (дата последнего
сканирования + совпадает ли `<title>` в выдаче с нынешним `<title>` шелла).

**1.2. Кластер hreflang между региональными сайтами БЕЗ участия апекса —
документированная конструкция, а не обходной манёвр.**

> «If it becomes difficult to maintain a complete set of bidirectional links for every
> language, you can omit some languages on some pages; **Google will still process the
> ones that point to each other.** However, it is important to link newly expanded
> language pages bidirectionally to the originating/dominant language(s).»
> «Alternate URLs do not need to be in the same domain.»
> — [ФАКТ — документация] https://developers.google.com/search/docs/specialty/international/localized-versions

Требования «мастер-домена», «главной версии» или обязательного участия апекса в
кластере в документации **нет**. Якорем служит «originating/dominant language» —
у нас это сильнейший региональный сайт. **Это выносит основную часть работы
из-под согласований целиком** и делает сценарий 1 непустым.

**1.3. Посылка вопроса раздела 4 перевёрнута.** Формулировка «редиректы на
региональные версии делать можно» документацией не подтверждается:

> «Avoid automatically redirecting users from one language version of a site to a
> different language version of a site. For example, don't redirect based on what you
> think the user's language may be. These redirections could prevent users (and search
> engines) from viewing all the versions of your site.»
> — [ФАКТ — документация] https://developers.google.com/search/docs/specialty/international/managing-multi-regional-sites

Редирект убрать нельзя (ограничение №2), поэтому вопрос не «делать ли», а «чем
компенсировать». Компенсация по документации — прямые нередиректящие ссылки на все
версии + взаимный hreflang. Региональные сайты этому уже удовлетворяют.

**1.4. Две «очевидные» идеи, которые ухудшили бы положение.** Обе выросли из
консенсуса, а не из замера, и обе поймал `devil`:

- **`204` → `451` на апексе.** `risk-comp` предлагал это первым приоритетом как
  «ужесточение, которое комплаенс согласует легче». Отозвано автором после проверки:
  > «All `4xx` errors, except `429`, are treated the same: Google crawlers inform the
  > next processing system that **the content doesn't exist**.»
  > — [ФАКТ — документация] https://developers.google.com/search/docs/crawling-indexing/http-network-errors
  ($451$ на этой странице не упомянут вообще.) Заявка целилась в единственный актив
  апекса — его присутствие в индексе. Плюс собственная поправка `risk-comp`:
  юрисдикционная позиция при `204` и при `451` **идентична**, различается только
  форма объявления.
- **Перенос редиректа на эдж без явного запрета на 301.** «Починив» редирект
  постоянным кодом, можно надёжно склеить самый сильный URL проекта с ротируемым
  зеркалом, закрытым `Disallow: /` и без канонизации [ФАКТ — замер, RS-IP]. Разницу
  301/302 здесь изначально не произнёс вслух никто.

**1.5. Основной документ репозитория содержит два неверных утверждения.**
`mostbet-redirect-scheme.md` §9 — подробно в разделе 8. Их надо исправить, иначе
следующая сессия унаследует ошибку ровно так же, как это было с `location.replace()`.

## 2. Вопрос раздела 4: ответ по документации Google

Проверено только по первоисточникам Google. Ни одного SEO-блога, ни одной цитаты
по памяти. Каждое утверждение ниже — либо дословная цитата, либо явно помеченный
вывод из цитат.

### 2.1. 301 или 302 для гео-редиректов

**Прямой рекомендации в документации Google нет.** Международные руководства не
называют ни одного HTTP-кода применительно к гео-редиректам, а страница про
редиректы не упоминает гео вообще. Вместо рекомендации документация даёт механику
последствий:

> **Permanent:** «Googlebot follows the redirect, and the indexing pipeline uses the
> redirect as a signal that the redirect target should be canonical.»
> **Temporary:** «Googlebot follows the redirect, but the indexing pipeline doesn't use
> the redirect as a signal that the redirect target should be canonical.»
> «Permanent redirects: Show the new redirect target in search results. / Temporary
> redirects: Show the source page in search results.»
> «Use permanent redirects when you're sure that the redirect won't be reverted.»
> «If you just want to send users to a different page temporarily, use a temporary
> redirect. This will also ensure that Google isn't influenced by the redirect which may
> help keep the old URL in its Search results.»
> — [ФАКТ — документация] https://developers.google.com/search/docs/crawling-indexing/301-redirects

> **301:** «Google follows the redirect, and Google systems use the redirect as a
> **strong** signal that the redirect target should be processed.»
> **302:** «By default, Google's crawlers follow the redirect, and Google systems use the
> redirect as a **weak** signal that the redirect target should be processed.»
> — [ФАКТ — документация] https://developers.google.com/search/docs/crawling-indexing/http-network-errors

**[ВЫВОД из цитат — не рекомендация Google]:** для гео-редиректа с апекса нужен
**302/307, и ни в коем случае не 301**. Два основания, оба дословные:

1. Мы хотим, чтобы в выдаче оставался источник, а не ротационное зеркало — это
   буквально определение temporary («Show the source page in search results»).
2. «Use permanent redirects when you're sure that the redirect won't be reverted» —
   цель гео-редиректа ротируется по определению [ФАКТ — со слов владельца], значит
   условие для permanent не выполнено.

301 на апексе означал бы передачу канонизации одноразовому зеркалу, которое закрыто
`Disallow: /` и не имеет ни `canonical`, ни `meta robots`, ни `X-Robots-Tag`
[ФАКТ — замер, RS-IP].

**Для 301-переклейки потерянных URL (вариант B) — другой случай**, это site move, и
permanent там уместен:

> «Keep the redirects for as long as possible, generally at least 1 year.»
> «we recommend that you use HTTP permanent redirects if possible, such as 301 and 308»
> «Don't redirect many old URLs to one irrelevant single URL destination, such as the home
> page of the new site. This can confuse users and might be treated as a soft 404 error.»
> «However, if you have consolidated content previously hosted on multiple pages to a new
> single page, you can redirect the older URLs to that new, consolidated page.»
> — [ФАКТ — документация] https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes

То есть **301 — да, но поштучно и по релевантности**, а не свалкой на один домен.

### 2.2. Достаточно ли hreflang на нередиректящей версии

hreflang — именно тот механизм, который Google называет решением этой задачи, и
формулировка на удивление прямая:

> «**What Google doesn't do:** Google crawls the web from different locations around the
> world. We do **not** attempt to vary the crawler source used for a single site in order
> to find any possible variations in a page. Therefore, make sure you explicitly tell
> Google about any locale or language variation that your site exposes, using one of the
> methods shown here (such as `hreflang` entries, ccTLDs, or explicit links).»
> «Don't use IP analysis to adapt your content. IP location analysis is difficult and
> generally not reliable.»
> — [ФАКТ — документация] https://developers.google.com/search/docs/specialty/international/managing-multi-regional-sites

Условия — жёсткие и дословные:

> «Each language version must list itself as well as all other language versions.»
> «If two pages don't both point to each other, the tags will be ignored. This is so that
> someone on another site can't arbitrarily create a tag naming itself as an alternative
> version of one of your pages.»
> «Alternate URLs must be fully-qualified, including the transport method (http/https).»
> «Alternate URLs do not need to be in the same domain.»
> «The three methods are equivalent from Google's perspective and you can choose the
> method that's the most convenient for your site.» (HTML-тег / HTTP-заголовок `Link` /
> XML-sitemap)
> «Only language codes listed in ISO 639-1 and region codes listed in ISO 3166-1 Alpha 2
> are supported.»
> «If you use codes that are listed as reserved for something else, Google Search ignores
> that part of the annotation.»
> — [ФАКТ — документация] https://developers.google.com/search/docs/specialty/international/localized-versions

**Прямой ответ: да, hreflang — документированный и достаточный способ сообщить о
всех локалях, но он ничего не гарантирует и требует четырёх вещей одновременно** —
взаимности, самоссылки, абсолютных URL и **обрабатываемого ответа от каждого
участника**. Последнее у нас и ломается: аннотация, указывающая на URL, который
отдаёт `204` или `451`, бессмысленна, потому что этот участник не может подтвердить
взаимность.

Гарантии нет прямым текстом:

> «Google might not crawl, index, or rank all your content for different locales.»
> — [ФАКТ — документация] https://developers.google.com/search/docs/specialty/international/locale-adaptive-pages

**Отдельно и важно:** «достаточно ли hreflang **на нередиректящей версии**» —
формулировка вопроса предполагает, что кластер держится на одной главной версии.
Документация такого не требует (см. 1.2). Кластер определяется попарной
взаимностью участников. Поэтому правильный ответ: **не «достаточно ли hreflang на
апексе», а «апекс для кластера вообще не нужен»**.

**Масштаб до 50 рынков** решается не разметкой на 50 сайтах:

> «A single sitemap that includes URLs for multiple websites, including sites from
> different domains.»
> «Make sure that you have verified ownership of all the sites that you will add in the
> sitemap.»
> — [ФАКТ — документация] https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap

Один XML на одном хосте покрывает весь кластер; взаимность обеспечивается структурой
файла, а не синхронностью 50 CMS. Цена — верификация владения всеми сайтами в
Search Console (при кросс-подаче через `robots.txt` верификация всех сайтов не
требуется, достаточно контроля над хостом, где лежит sitemap).

### 2.3. Как это сочетается с тем, что редирект на JS

Утверждение из `mostbet-redirect-scheme.md` §9 «Google трактует JS-редирект
аналогично 301» **дословно не подтверждается**. Слова «301» применительно к JS в
документации нет. Что есть на самом деле:

> «The following table explains the various ways you can use to set up permanent and
> temporary redirects, **ordered by how likely Google is able to interpret correctly**»
> «Only use JavaScript redirects if you can't do server-side or `meta refresh` redirects.»
> «While Google attempts to render every URL Googlebot crawled, rendering may fail for
> various reasons. This means that if you set a JavaScript redirect, **Google might never
> see it** if rendering of the content failed.»
> — [ФАКТ — документация] https://developers.google.com/search/docs/crawling-indexing/301-redirects

При этом `JavaScript location` **действительно отнесён к группе постоянных
редиректов** — это проверили независимо `seo-arch` и `devil`. Корректная формулировка,
которая и должна попасть в документы:

> JS-`location` классифицирован Google как постоянный редирект, но стоит **в конце
> списка по надёжности интерпретации**, и Google прямо предупреждает, что может его
> вообще не увидеть.

**Как это складывается с гео и `204`.** Из США редирект физически не происходит:
API отдаёт `204`, условие `Ce != null && Ce.redirect` не выполняется [ФАКТ — замер,
US-IP]. То есть бот из основной точки выхода не видит ни редиректа, ни контента, ни
разметки — он видит пустоту с кодом успеха. Это и есть худший из возможных исходов:

> «If the content suggests an error for Google Search, an empty page or an error message,
> Search Console will show a soft 404 error.»
> — [ФАКТ — документация] https://developers.google.com/search/docs/crawling-indexing/http-network-errors

**[ГИПОТЕЗА, требующая Search Console]:** апекс мог уйти в **soft 404** — и не только
в США, но и там, где отдаёт `200`, потому что шелл 9.5 KB без индексируемого текста —
это ровно «an empty page» по формулировке Google. Эта версия объясняет обвал индекса
лучше остальных, и именно поэтому её нельзя записывать в выводы, пока не открыт отчёт
«Страницы» в Search Console.

### 2.4. Чего в документации Google НЕТ — не выдавать за документированное

- Рекомендации 301 vs 302 **конкретно для гео-редиректов** — ни одного упоминания кода.
- Фразы «JS-редирект = 301».
- Утверждения «гео-редирект легитимен, Google его прямо допускает» — там «Avoid».
- Требования, чтобы hreflang-альтернат был **открыт в `robots.txt` или не имел
  `noindex`**. Это популярное убеждение, но на странице про localized versions его нет.
- Различия между `location.href` и `location.replace()`.
- Определения, что считается «blocking requests from the United States» — **триггер
  переключения краула на не-US-адреса нигде не описан**. Проверялось специально.
- Ответа, читает ли Google заголовок `Link:` на ответе `204` (цитата про `204` скорее
  против).
- Упоминания `451` в перечне статус-кодов — его там нет вообще.
- Требования, чтобы в hreflang-кластере был мастер-домен или апекс.

## 3. Сценарий 1: ничего не разрешили

Апекс не трогаем вообще. Вопреки первому впечатлению, сценарий **не пустой** — но
только потому, что находка 1.2 выносит кластер из-под согласований.

### Схема 1A — «Кластер без апекса» (основная)

| шаг | что делаем | согласование |
|---|---|---|
| 0 | **Замер-предусловие:** `curl -I` по всем региональным доменам **с US-IP и с RS-IP** | не нужно |
| 0-бис | Резолв и замер `mostkaei.com` с RS-IP | не нужно |
| 1 | Матрица соответствий **URL↔URL** между региональными сайтами | не нужно |
| 2 | Взаимный hreflang внутри кластера регионалок, **без апекса** | не нужно |
| 3 | `x-default` — либо не ставить, либо на сильнейшую регионалку | не нужно |
| 4 | Видимые ссылки-переключатели языка/региона между регионалками | не нужно |
| 5 | Явный путь восстановления «не открывается? → `mostbet.com`» | не нужно |
| 6 | Живой переход «играть» через свой эндпоинт-редиректор на том же хосте, `rel="nofollow"` | не нужно |
| 7 | Инструментовать вход замерами (Navigation Timing / HAR с RS-IP) | не нужно |

**Шаг 0 блокирующий.** Если региональные сайты тоже отдают `204`/`451` с US-IP —
кластер невидим целиком и половина плана отменяется. Стоит десять минут, а отменить
может недели работы. Замер `mostbet-pl.com` в `BRAINSTORM-setup.md` §6 сделан **без
указания точки выхода**, поэтому опереться на него нельзя.

**Шаг 1 — не формальность, а основная трудоёмкость.** hreflang аннотирует
**страницу**, а не сайт. Лендинг ~970 слов и статейник из 4–8 страниц под другой
интент альтернатами не являются. Начинать с гарантированного соответствия
главная↔главная, дальше по совпадающим интентам. Объём этой работы **[НЕИЗВЕСТНО]** —
инвентаризации своих сайтов ни у кого нет.

**Доставка hreflang.** Три способа равнозначны для Google, поэтому выбор чисто
операционный: XML-sitemap (один файл, Search Console API, не листится в `robots.txt`)
против тегов в `<head>` 50 CMS. `infra-block` за sitemap — он не выкладывает список
живых доменов в HTML каждой страницы. Оговорка, которую он сам сделал: «сложнее
спарсить» ≠ защита.

**Что даёт:** индексируемый связный слой из доменов, у которых уже есть возраст,
ссылки и контент. Не надо ничего создавать — надо связать.
**Чего стоит:** матрица URL↔URL + верификация доменов в Search Console.
**Риск:** если регионалки закрыты с US-IP — не работает (шаг 0); если контент между
версиями слишком разный — аннотации формально некорректны.
**Начать сегодня:** шаги 0, 0-бис, 1.

### Схема 1B — «Якорь на guidebook» (если доступ есть)

`guidebook.mostbet.com` — единственный, кто реально сидит в выдаче, и у него уже
исправный `canonical` и hreflang на 13 языков [ФАКТ — замер]. Под редирект он не
попадает, потому что гейт сравнивает хост на точное совпадение. Если доступ к нему
прямой — это готовый «originating/dominant» якорь кластера, и схема 1A получает
центр тяжести с реальным индексом.

**[НЕИЗВЕСТНО] — есть ли у нас прямой доступ к `guidebook`.** Во вводных это не
задано, а разница принципиальная: поддомен апекса, но собственный WordPress. Вопрос
первого приоритета, стоит одного письма.

**Оговорка `devil`:** «guidebook реально сидит в выдаче» стоит на **одной** брендовой
выдаче, снятой в один момент из одной точки. Ранжирование по коммерческим запросам
не проверено. Строить на нём центр тяжести можно, объявлять его сильным — нельзя.

## 4. Сценарий 2: разрешили только 301-переклейку

Всё из сценария 1 остаётся в силе и делается параллельно — оно ни от чего не зависит.

### Предупреждение, которое должно стоять раньше плана

**Сценарий 2 может не иметь предмета.** Автор идеи сам не уверен, что на
`mostbet.com` осталось что-то кроме главной [`BRAINSTORM-setup.md` §2]; карты URL нет
[ФАКТ — ответ владельца]; sitemap с US-IP отдаёт `204` [ФАКТ — замер]. Требование
`devil`, которое я разделяю: **не выносить сценарий 2 на согласование, пока не
закрыт замер «сколько страниц реально осталось»** — иначе команда просит ресурс под
работу, объём которой неизвестен и может оказаться нулевым.

Отдельно: 301-переклейка касается **потерянных URL**, но никогда не корня апекса —
`mostbet.com/` обязан остаться входом (ограничение №2).

### Схема 2A — поштучная переклейка на релевантные регионалки (предпочтительная)

Каждый восстановленный URL клеится 301 на страницу того регионального сайта, которая
закрывает тот же интент и тот же язык. Где соответствия нет — **не клеить вовсе**.
Основание дословное: «Don't redirect many old URLs to one irrelevant single URL
destination… might be treated as a soft 404 error».

**Что даёт:** возвращает сигналы туда, где они сразу работают на индексируемый слой,
и попутно усиливает кластер из сценария 1.
**Чего стоит:** восстановление карты URL — самая трудоёмкая часть; плюс ручное
сопоставление.
**Риск:** карта может оказаться почти пустой.

### Схема 2B — консолидатор (когда поштучного соответствия нет)

Один домен-приёмник, на нём — структура под потерянные интенты, дальше hreflang в
общий кластер. Кандидаты и честная оценка:

| кандидат | за | против |
|---|---|---|
| `mostbett.bet` (наш) | доступен, открыт, свой sitemap, `canonical` на себя | 6 URL — это не сайт; сейчас он ещё и цель битого `x-default` |
| новый домен | чистая структура под задачу | ноль возраста и ссылок — худший приёмник сигналов |
| сильнейшая регионалка | возраст, ссылки, контент | смешивает гео-таргетинг с ролью консолидатора |

`mostbet.bet` (одна «t») — **вне схемы при любом сценарии**: принадлежность
неизвестна. Требование `risk-comp`, поддержанное документацией: взаимность hreflang
построена Google именно как защита от того, чтобы посторонний сайт объявлял себя
вашей версией.

### Рамки, без которых 301 просить нельзя

Формулировка `risk-comp`: 301 сильнее hreflang, потому что это **HTTP-уровневое
утверждение о переносе идентичности**, потребляемое браузерами, кэшами, архивами и
базами ссылочных профилей. Откатывается несопоставимо труднее, чем снятие тега.
Решение принимается как о **необратимом**.

1. **Цель 301 — домен, с которым мы готовы быть публично отождествлены навсегда.**
   Это исключает ротационные зеркала (301 на ротируемый хост — сломанное «постоянное»
   заявление, вдобавок публично сжигающее зеркало) и исключает `mostbet.bet`.
2. **Только неглавные URL, корень не трогаем.** Ограничение №2 не нарушается — и
   именно так заявку и надо подать, чтобы она не выглядела угрозой для другой команды.
3. **301 применяется только там, где эдж уже обслуживает рынок.** Иначе мы
   маршрутизируем закрытое гео на живой сайт. Это конкретное комплаенс-возражение к
   наивной переклейке, и снять его надо в тексте заявки заранее, а не в ответ.
4. Предусловие — восстановление карты URL.

### Восстановление карты URL — отдельная задача, а не предусловие «на веру»

Search Console (заявкой в другую команду) → Wayback Machine → исторические выгрузки
Ahrefs/Semrush → профиль внешних ссылок → внутренние ссылки с `guidebook`.
**Можно начать сегодня** всё, кроме Search Console.

**Срок жизни редиректов:** «Keep the redirects for as long as possible, generally at
least 1 year». Планировать надо не разовую акцию, а год поддержки.

## 5. Сценарий 3: чиним всё

Всё из сценариев 1 и 2 плюс пакет правок на апексе. **Пакет идёт одной заявкой** —
доступ к апексу узкое горлышко, и если разметка уйдёт первой заявкой, а остальное
второй, второй не будет.

Порядок внутри пакета продиктован принципом `risk-comp`: **первым просить то, что
ничего не меняет в проде**.

| # | что просим | почему это согласуемо |
|---|---|---|
| 0 | **read-only:** выгрузка Search Console, логи эджа по Googlebot за 30 дней, **дословный текст ограничения комплаенса** | ничего не меняется, отказать не на чем |
| 1 | **удалить** `x-default` → `mostbett.bet` и невалидные альтернаты | удаление ошибочного заявления, новых не добавляется |
| 2 | self-canonical `https://mostbet.com/` | утверждение только о самом URL: ни страны, ни стороннего домена, ни взаимности |
| 3 | для закрытых гео отдавать `200` с **побайтово тем же телом**, что и в открытых | материалов не добавляется ни для кого; устраняет расхождение HTML между странами |
| 4 | hreflang, формируемый **автоматически из действующего гео-списка эджа** | новое решение о рынках не запрашивается, разметка приводится в соответствие с уже принятым |
| 5 | 301-переклейка — отдельным документом и последней | самая тяжёлая и самая долгоживущая правка |
| 6 | JS-редирект → серверный **302/307** на эдже | см. ниже |
| ~~7~~ | ~~`robots.txt` одинаковый из всех гео~~ | **изъят во второй итерации** — основание отозвано, расхождение по классу клиента, а не по локали |
| ~~8~~ | ~~`<noscript>` с навигационным элементом~~ | **из пакета удалено** — вето `risk-comp`, см. раздел 6-бис |

**Шаг 3 — предусловие для 2 и 4.** Пока апекс отдаёт `204`, любая разметка в `<head>`
физически не доезжает до основной точки выхода Googlebot. Честная оговорка, которую
надо назвать самим: закрытый рынок начнёт получать брендированный `<title>` вместо
пустоты. Дельта мала, но не нулевая.

**Шаг 4 — правило согласованности вместо списка доменов:** альтернат публикуется для
страны тогда и только тогда, когда `/api/v3/common/redirect` для неё возвращает
`{"redirect":true}`. Критерий масштабируется до 50 рынков без новых согласований;
список требует новой заявки на каждый рынок. Адресат альтерната — **долгоживущий
региональный сайт, никогда ротационное зеркало**.

### Открытый конфликт внутри пакета — решать до подачи

Шаги 3 и 4 вместе дают результат, против которого `risk-comp` возражает отдельно.
Шаг 3 требует отдавать закрытым гео **побайтово то же тело**, что и открытым; шаг 4
кладёт в это тело hreflang. В сумме перечень обслуживаемых рынков начинает
доставляться внутрь намеренно закрытой юрисдикции — а именно этот довод
(«разметка не доезжает до закрытых гео бесплатно, отдельный фильтр не нужен»)
`risk-comp` кладёт в заявку как аргумент в нашу пользу.

Развести по User-Agent **нельзя** — это красная линия 6.1. Варианты, между которыми
надо выбрать до подачи заявки, а не после:
- отдавать закрытым гео `200` с телом **без** hreflang (тогда тела не побайтово
  одинаковые, и довод шага 3 «ничего не добавляется» слабеет);
- отдавать одинаковое тело с разметкой и принять дельту явно;
- не просить шаг 4 вовсе и оставить кластер на регионалках (сценарий 1).

> ⚠ **Во второй итерации конфликт РАЗРЕШЁН.** Он существовал только в сценарии
> «выравнивать вверх». При выравнивании **вниз** (заявка №3′) в закрытых гео тела нет
> вообще — доставлять нечего, и шаг 4 перестаёт упираться в шаг 3, оставаясь вопросом
> только для открытых гео, где он безобиден. Это единственный пункт первой версии
> отчёта, помеченный «спором не разрешён», который вторая итерация **решила**, а не
> усложнила.

### Тексты заявок (формулировки `risk-comp`, дословно)

Принцип очерёдности: **первым просить то, что ничего не меняет в проде.**

> ⚠ **Вторая редакция очереди.** Появилась позиция **вне очереди** — это не заявка,
> а инцидент. Заявка №3 переписана. Пункт «одинаковый `robots.txt` из всех гео»
> **изъят** из пакета: `devil` отозвал основание, которое сам же дал, и был прав —
> файл отдаётся из США полностью и согласованно с RS, а расхождение идёт по **классу
> клиента**, а не по локали, так что цитата «must specify the same rules in each
> locale» нашу картину не описывает.

**Вне очереди — инцидент И-1. Подавать не как SEO-запрос и не в общем пакете.**
> С IP, классифицируемого эджем как US, `https://mostbet.com/` отдаёт `204` обычному
> браузеру и `200` с полным документом клиенту, в `User-Agent` которого присутствует
> подстрока `Googlebot/2.1`. Под тем же UA `/api/v3/common/redirect` возвращает
> `{"redirect":true,"domain":"…"}` — **работающий маршрут в сервис**, в то время как
> сам целевой домен отвечает `451`. Сверки по обратному DNS и по диапазонам Google
> нет. Просим устранить: ответ сервиса не должен зависеть от строки `User-Agent` при
> неизменной стране запроса. Приоритет — сначала API, затем HTML.

Слов «клоакинг», «обходится подстановкой строки», «presenting different content» в
тексте И-1 быть не должно: разница бинарная «есть ответ / нет ответа», тело идентично
тому, что отдаётся в открытом гео. Предъявлять сильнее замера здесь нельзя.

**Заявка №0 — read-only. Отказать не на чем.**
> Просим предоставить (без изменений в конфигурации): 1) доступ или выгрузку Search
> Console по `mostbet.com` — отчёт «Страницы»: категория soft 404, дата последнего
> сканирования главной, динамика покрытия за последние 3 месяца; 2) выборку из логов
> эджа: обращения Googlebot за последние 30 дней с разбивкой по стране источника;
> 3) **дословную формулировку действующего ограничения по размещению материалов на
> `mostbet.com`** — с указанием, кем и когда оно установлено.

Пункт 3 — самый важный во всём документе. Текста запрета нет ни в одном из четырёх
файлов репозитория, есть только пересказ. **Мы спорим о документе, которого никто
не видел.**

> ⚠ **Вторая редакция заявки №0.** Добавлены пункты, и один из них встал **первым во
> всём проекте**:
>
> **0. Search Console → «Меры, принятые вручную» и «Проблемы безопасности».** Один
> экран. Находка `devil`: пятое объяснение обвала — **санкция** за клоакинг или
> sneaky redirects. Под действующей санкцией чинить разметку бессмысленно, поэтому это
> **гейт перед всей работой**, а не пункт в очереди. `seo-arch` принял немедленно, но
> отклонил ранжирование этой версии выше механических: направление подмены обратное
> тому, что описывают спам-политики (краулеру достаётся *хуже*, а не лучше),
> и элемент намерения не установлен.
>
> **2-бис.** Логи эджа — с разбивкой не только по стране, но и **по строке
> `User-Agent`**, с идентификатором сработавшего правила и ASN.
>
> **2-тер. Сам ruleset эджа** (read-only) — упорядоченный список правил, условия и
> ответ каждого. Мы дважды реконструировали конфиг по поведению и дважды ошиблись.
> Логи говорят, что случилось; конфиг говорит, **что может случиться**. Дешевле логов.
>
> **3 расщеплён на 3а–3д:** 3а — дословный текст ограничения, кем и когда установлен;
> **3б — предписывает ли он удаление материалов для ВСЕХ аудиторий или нейтральный
> ответ для ПЕРЕЧИСЛЕННЫХ юрисдикций** (это два несовместимых ограничения, а у нас
> записано первое); 3в — закрытый перечень юрисдикций из документа; **3г — по каждой
> стране: закрываем мы на эдже или блокирует местный регулятор у провайдеров**
> (две категории требуют противоположных правил, и Литва — первая строка этого
> столбца); 3д — кто и когда проверял, что пользователь из этих стран видит
> предписанное.
>
> **4.** Список доменов, заявленных в CGA как домены, на которых предлагаются игры
> (LOK: отдельная заявка и сбор EUR 250 за домен), и процедура регистрации нового
> зеркала при ротации.
>
> **5.** Кто и когда утвердил действующий гео-список эджа и на каком документе он
> основан.
>
> **6.** Доступ к Яндекс.Вебмастеру: апекс в нём верифицирован
> (`<meta name="yandex-verification">`, секция `User-agent: Yandex`, `Host:`,
> `Clean-param:` в `robots.txt`). Это **второй независимый источник старой карты URL**
> помимо Search Console, и в первой версии отчёта его не было вообще.

**Заявка №1 — снятие ошибочного заявления. Подавать как исправление дефекта.**
> В `<head>` `mostbet.com` присутствует аннотация
> `<link rel="alternate" hreflang="x-default" href="https://mostbett.bet/">` и ещё 20
> аннотаций, описывающих конфигурацию, которая не соответствует фактическому поведению
> сервиса. Просим удалить аннотацию `x-default`. Это удаление публикуемого утверждения,
> новых утверждений не добавляется.

**Заявка №2 — self-canonical.**
> Просим добавить `<link rel="canonical" href="https://mostbet.com/">`. Тег является
> утверждением исключительно о самом этом URL: не называет ни одной страны, ни одного
> стороннего домена, не требует взаимных ссылок, не изменяется при изменении числа
> рынков.

**~~Заявка №3 прежней редакции~~ — УМЕРЛА.** Просила `200` с тем же телом для закрытых
гео. Опора («закрытые гео не получают ничего») оказалась ложной, а `204` для США —
не дефект, а **предписанное Google поведение**: «your server should block Googlebot if
it appears to be coming from the USA». Снята автором (`seo-arch`) по документации.

**Заявка №3′ — выровнять ответ вниз.** Заменяет прежнюю, сливается с И-1.
> Просим устранить различие ответа по классу клиента в пределах одной страны: в
> закрытых гео `204` отдаётся **всем** клиентам без исключения, включая любые
> краулерские `User-Agent`.

Это **сужение** выдачи, а не расширение — комплаенс не может это отклонить, не признав
дефект. Цена названа прямо: апекс теряет остаточное присутствие в индексе.

**Заявка №4 — hreflang по правилу согласованности.**
> Просим формировать набор `hreflang` **автоматически из уже действующего гео-списка
> эджа**: альтернат публикуется для страны тогда и только тогда, когда
> `/api/v3/common/redirect` для неё возвращает `redirect:true`. Новое решение о рынках
> не запрашивается — разметка приводится в соответствие с решением, уже принятым и
> развёрнутым. Адресатом альтерната является долгоживущий региональный сайт, **не**
> домен, выдаваемый механизмом редиректа.

**Заявка №5 — 301, отдельным документом и последней** (рамки — в разделе 4).

### Шаг 6 отдельно: перенос редиректа на эдж

**За** — единогласно (`seo-arch`, `infra-block`, `product-ux`), и подпёрто
документацией: «Only use JavaScript redirects if you can't do server-side or
`meta refresh` redirects». Гео уже решается на эдже [ФАКТ — `server-timing:
country;desc="RS"`, домена в HTML нет, grep 0], то есть логику переносить не надо —
она уже там.

**Что даёт:** минус один round-trip и загрузка бандла; исчезает `noscript`-тупик;
исчезает ловушка повторного редиректа; уходит риск «Google might never see it».

**Что НЕ даёт** (не выдавать за полное решение): в закрытом гео редиректить некуда,
`204` остаётся `204`.

**Блокирующие условия, без которых выкатывать нельзя:**

1. **302/307, никогда 301.** Иначе апекс склеивается с `Disallow: /`-зеркалом
   надёжно и, по признанию `infra-block`, несимметрично откатывается.
2. `Cache-Control: private, no-store` + **страна в ключе кэша**. Закэшированный
   `Location` увозит человека в чужую юрисдикцию — это комплаенс-инцидент, не UX-баг.
3. Никакого ветвления по User-Agent (см. раздел 6).
4. Поэтапная выкатка по проценту трафика и по странам с мгновенным откатом: эдж бьёт
   по 100% сразу, канареек по версии бандла там нет.
5. **Закрыть до выкатки:** Googlebot начнёт получать 302 на домен с `Disallow: /`.
   Что при этом происходит с сигналами — в документации прямо не описано
   **[НЕИЗВЕСТНО]**.

**Приоритет понижен по ходу спора.** Изначально за эдж-редирект высказались трое
(`seo-arch`, `infra-block`, `product-ux`) — без единого замера. `devil` показал, чего
не сказал никто: сегодня редирект сделан **самым слабым и наименее надёжно
интерпретируемым** способом, и, возможно, именно поэтому апекс ещё не склеился с
зеркалом. «Починка» заменяет слабый сигнал на надёжный, направленный в мусорный
ротируемый домен с `Disallow: /` и без канонизации. `product-ux` согласился и сам
понизил пункт из «первоочередное» в **«требует SEO-заключения до выкатки»**.

**Проверенный и отвергнутый обходной путь:** направить эдж-302 не на одноразовое
зеркало, а на долгоживущий региональный сайт. Отвергнут самим `product-ux`:
региональные сайты открыты для индексации, а значит с высокой вероятностью и
заблокированы у провайдеров в тех же гео, где зеркала и нужны. Это **[ГИПОТЕЗА]**,
опровергнуть её может только замер доступности регионалок из рабочих гео — но пока
она стоит, вариант чинит SEO и ломает доступ.

## 6. Сквозные красные линии

Действуют во всех трёх сценариях, согласованы всеми участниками.

**6.1. Условие любой дифференциации — страна, не клиент.** Формулировка `risk-comp`,
которая должна стоять в заявке дословно, потому что реализовывать будут не
SEO-специалисты, и «сделать проще» для них означает «проверить UA»:

> Условием любой дифференциации ответа является **страна запроса, определяемая на
> эдже** — тот же механизм, что уже используется (`server-timing: country`).
> Дифференциация по `User-Agent`, по имени бота, по обратному DNS или по любому иному
> признаку «это поисковый робот» **недопустима ни в каком виде**.

> ⚠ **Вторая редакция.** Прежний текст заканчивался словами «Сейчас различий по
> `User-Agent` нет… и это состояние необходимо сохранить». **Посылка оказалась
> ложной** (раздел 0): различие существует и измерено. Сохранять нечего — его надо
> **устранять**. Принцип не изменился, знак заявки сменился на противоположный:
> не «сохраните», а «устраните ветвление по классу клиента».

Целевое состояние: ответ сервиса **не зависит от строки `User-Agent` при неизменной
стране запроса**. Выравнивание — **вниз** (в закрытых гео `204` всем без исключения),
а не вверх. Обоснование `risk-comp`: выдача документа краулеру в закрытой юрисдикции
производит **долгоживущий публичный артефакт** — запись в местной выдаче по бренду, а
признак «оператор таргетирует рынок» регулятор устанавливает по наблюдаемому снаружи.
Отдавать документ роботу в закрытой стране — риск **больше**, чем человеку, а не
меньше. Цена названа прямо: апекс теряет остаточное присутствие в индексе с основной
точки выхода Googlebot.

Различие по стране штатно; различие по клиенту — клоакинг:

> «Cloaking refers to the practice of presenting different content to users and search
> engines with the intent to manipulate search rankings and mislead users.»
> — [ФАКТ — документация] https://developers.google.com/search/docs/essentials/spam-policies

**6.2. Ротационные зеркала — никогда в публичной разметке.** Ни hreflang, ни sitemap,
ни внутренние ссылки, ни футеры. Аргумент не «протухнут» (частота ротации не
измерена), а прямой: зеркало отдаёт `Disallow: /` и не имеет ни `canonical`, ни
`meta robots`, ни `X-Robots-Tag` [ФАКТ — замер, RS-IP] — в кластере такой участник
не работает с первого дня.

**6.3. Реестр доменов физически разделён на два класса** — «долгоживущие,
публикуемые» и «ротационные, непубликуемые», флаг на уровне записи, проверка **в
пайплайне**, а не устная договорённость. Иначе ротация начнёт вписывать зеркала в
разметку сама. Вывод домена из кластера — процедура (сначала убрать из аннотаций у
всех остальных, потом гасить), а не удаление строки.

**6.4. Не менять `204` на `451`** и предупредить об этом владельца отдельной строкой —
как предохранитель от чужого «улучшения», а не как заявку:

> `204` на апексе — код успеха; замена его на `451` вероятно означает удаление апекса
> из индекса. Если кто-то планирует унификацию с зеркалом — сначала к нам.

**6.5. Не клеить много URL на один нерелевантный приёмник** — прямая цитата про
soft 404 в разделе 2.1.

**6.6. Язык заявок.** Слова, которых в них быть не должно: «SEO», «позиции»,
«ранжирование», «ссылочный вес», «трафик», «зеркало», любые имена ротационных
доменов. Для согласующего всё это читается как «просим больше видимости», то есть как
рост риска. И главное: **просить надо критерий, а не список доменов** — критерий
масштабируется до 50 рынков без новых согласований, список требует новой заявки на
каждый рынок.

**6.7. `mostbet.bet` (одна «t») — вне любой схемы**, пока принадлежность не
установлена. Взаимность hreflang означала бы, что посторонний управляет нашей
атрибуцией: Google построил требование взаимности именно как защиту от этого
(«This is so that someone on another site can't arbitrarily create a tag naming itself
as an alternative version of one of your pages»).

## 6-бис. Согласованный отрицательный результат

Его надо предъявить владельцу проекта прямо, потому что это цена его же ограничений.

**Тупик при выключенном или упавшем JS на апексе неустраним** — но формулировка первой
версии была неточна в трёх местах, и вторая итерация её исправила.

> ⚠ **Правка 1.** Правильно: «неустраним **для пользователя без JS**; для пользователя
> **с JS в гео, где редиректа нет**, состояние **не измерено ни разу**».
>
> ⚠ **Правка 2.** Атрибуция «решения нет, пока держатся ограничения №1 и №2» —
> **неверна**. Ни одно из трёх вето на ограничение №1 не опиралось: `meta refresh`
> закрыт публикацией имени ротационного домена, селектор снят за публикацию перечня
> рынков, `<noscript>` — за направление заявления. `product-ux` поймал это у себя сам.
>
> ⚠ **Правка 3.** Вето на `<noscript>` больше **не абсолютное, а условное** (В1′,
> формулировка `risk-comp` дословно): *`<noscript>` на апексе разрешён, если и только
> если его адресат — долгоживущий региональный сайт, а страна ответа определяется на
> эдже.* Вето касалось закрытых юрисдикций; в открытых его не было никогда. Остаточный
> риск теперь **измеримый** (заблокированы ли регионалки у провайдеров в рабочих гео),
> а не согласуемый.

**Второй тупик, которого в первой версии не было.** Объяснить что-либо человеку в
закрытом гео невозможно **ни в какой форме**: показать ему можно только тем же
ответом, который получит краулер (различие по клиенту запрещено линией 6.1), а этот
ответ и есть публичный артефакт внутри закрытой юрисдикции. Замкнуто по построению,
а не по вето.

**Остался один непроверенный ход**, решение за комплаенсом: `200` + минимальный
нейтральный текст, одинаковый всем клиентам, + `X-Robots-Tag: noindex` — краулер
получает байты вместе с инструкцией не показывать страницу, публичный артефакт не
возникает, 6.1 не нарушается. [ФАКТ — документация] «Any rule that can be used in a
robots `meta` tag can also be specified as an `X-Robots-Tag`»; `noindex` = «Do not show
this page, media, or resource in search results»
(https://developers.google.com/search/docs/crawling-indexing/robots-meta-tag).
Три довода против назвал сам автор идеи: директива ≠ гарантия и она только про Google;
механизм риска может быть шире поисковой выдачи; `204` стоит ноль и уже развёрнут.

### Названный класс пострадавших от выравнивания вниз

Найдено на последнем ходу в `robots.txt` апекса [ФАКТ — замер, US-IP + UA-дверь]:
`Disallow: /*profile/` и `Disallow: /*resetting/` — личный кабинет и **сброс пароля**.
Файл статический, зеркало его не обслуживает, значит это **ископаемое апекса**.

Следствие: ссылка из письма о сбросе пароля ведёт на `mostbet.com/resetting/<токен>`,
и такие письма лежат у людей в ящиках сейчас. Гейт сохраняет path — в рабочем гео,
вероятно, ещё работает; при выравнивании вниз в закрытом гео отдаст **ноль байт**.

`risk-comp` рассмотрел и **сузил свой же вердикт «вниз»**: он относится к индексируемой
публичной поверхности и маршруту в игровой сервис, но **не к аутентифицированному пути
действующего клиента** — у `/resetting/<токен>` нет свойства публичного артефакта
(закрыт `Disallow:`, адрес токенизирован, в выдачу не попадает). Первоисточник, в
отличие от гипотезы про обязательное раскрытие, здесь есть — LOK, PB 2024 no. 157:
Artikel 5.7 (`waarborgfonds` для выплаты средств игроков), Artikel 5.3 (право жалобы
в течение шести месяцев), Artikel 5.5 (право Кюрасао и его суд).

Три ограничения, под которыми это поддержано: **(а)** из этого **не следует апекс** —
обязанности лежат на лицензиате и игровом сервисе, канал может быть любым;
**(б)** только **read-only + exit-only** (баланс, вывод, закрытие аккаунта, поддержка;
ни депозита, ни игры, ни бонусов); **(в)** отдельный трек, **в SEO-пакет не входит и
рычагом для возврата контента на апекс служить не может**.

Как к этому пришли. Пользователь с выключенным JS остаётся на 9 573 B с
`<noscript>You need to enable JavaScript to run this app.</noscript>`, перехода не
происходит никогда [ФАКТ — замер, RS-IP]. Чинится это тремя способами, и все три
закрыты:

| способ | кем закрыт | почему |
|---|---|---|
| видимая ссылка в `<noscript>` | `risk-comp`, вето | направление заявления противоположно: `451`-заглушка говорит «здесь нельзя» и сокращает экспозицию, ссылка говорит «здесь можно, вот как» и увеличивает |
| селектор стран / языков | снят самим `product-ux` | видимый перечень обслуживаемых рынков — самое опасное из всего обсуждавшегося |
| `<meta http-equiv="refresh">` | `risk-comp` + `infra-block` | публикует имя домена назначения в статическом HTML, которого там сейчас нет намеренно [ФАКТ — grep `8unx689` по исходному HTML, 0 совпадений] |

Остаётся только серверный редирект (шаг 6 сценария 3), у которого своя цена.
`product-ux` вето принял и обходных путей не искал — весь пласт уходит на
региональные сайты.

**Что при этом было опровергнуто в пользу ограничений:** `product-ux` пытался
опереться на «право пользователя беспрепятственно покинуть сервис». `risk-comp` отвёл

по построению существует только на открытых рынках, где мы работаем легально**
[ФАКТ — замер, US-IP + код гейта]. Юрисдикционного измерения у неё нет. Рычаг снят.
